# Реализация поведения в verba

Поведение verba задаётся не кодом, а цепочкой, и код — последнее звено:

```
docs/requirements.md      BR-19. Пользователь может удалить свою запись…
      │  тег @BR-19
docs/features/*.feature   Сценарий: подтверждённое удаление необратимо
      │  текст строки = шаблон шага
steps/{common,domain,e2e}/ When('я удаляю запись и подтверждаю удаление', …)
      │  вызов
src/server/               deleteRecording(user, id)
```

Сценарий — это и есть тест. Статус требования вычисляется прогоном: «BR-19
реализовано» значит «все сценарии с `@BR-19` зелёные». Если цепочка
рвётся, агент следующей сессии прочитает спеку, которая врёт, и будет
уверенно строить на ней. Поэтому работа всегда идёт сверху вниз.

Решения, на которых это стоит: [ADR 0002](../../../docs/decisions/0002-stack-and-hosting.md)
(стек), [ADR 0003](../../../docs/decisions/0003-executable-scenarios.md)
(сценарии и раннер). Модель данных — в `docs/architecture.md`, правила
вёрстки — в `AGENTS.md`.

## Цикл

1. **Найти требование и его сценарии.** `grep -rn "@BR-19" docs/features`.
   Если задача сформулирована без номера («почини удаление папки») —
   найти требование по смыслу в `docs/requirements.md`.

2. **Если поведение меняется — сначала сценарий.** Новое или изменённое
   поведение сначала появляется в `.feature` (и в BR, если меняется само
   требование), потом в коде. Если сценария под задачу нет, а требование
   есть — написать сценарий и показать его пользователю до кода: это
   самое дешёвое место, чтобы поймать непонимание.

3. **Определить уровень.** Сценарий без тега — доменный: шаги вызывают
   сервисы напрямую, в процессе, против тестовой базы. `@e2e` — нужен
   запущенный сервер: экран (`page`) или HTTP-слой (`request`), например
   лимиты тела запроса при загрузке. Пограничный случай — в пользу домена.

4. **Шаги.** Сначала поискать готовую фразу в `steps/` — словарь общий,
   и одна и та же мысль, записанная двумя разными фразами, удваивает
   поддержку. Подготовка данных (`Дано`) — в `steps/common/`, прямо в
   базу. `Когда`/`Тогда` — в `steps/domain/` или `steps/e2e/`.

5. **Убедиться, что тест красный по правильной причине.** `test:spec`
   (или `test:e2e`). Падение должно говорить «поведения нет», а не
   «шаг не найден» или «база не поднялась». Тест, который ни разу не был
   красным, ничего не доказывает.

6. **Реализовать в `src/server/`.** Логика — в сервисах. Route handlers,
   серверные компоненты и воркер только достают входные данные и
   вызывают сервис.

7. **Зелёный прогон.** `test:spec`; если трогали `@e2e` — `test:e2e`.
   Потом проверка покрытия (команда в `docs/features/README.md`).

### Если сценарий кажется неправильным

Не править `.feature` так, чтобы он совпал с написанным кодом. Это ровно
тот дрейф, от которого защищает вся цепочка: тест зелёный, а требование
тихо поменялось. Если сценарий противоречит требованию, макету или
здравому смыслу — остановиться и сказать пользователю, что именно не
сходится, с предложением правки. Меняется сценарий только вместе с
осознанным решением, а при правке BR — все сценарии с его тегом.

## Шаг `Тогда` проверяет наблюдаемый результат

Машина проверяет, что у фразы есть реализация и что она не падает. Она не
проверяет, что реализация что-то проверяет. Пустой или косвенный `Тогда`
делает сценарий зелёным и лживым — хуже, чем отсутствие теста, потому что
создаёт уверенность.

Наблюдаемый результат — то, что увидел бы пользователь или оператор:
строки в базе, файл на диске, текст на экране, HTTP-ответ.

```ts
// плохо: проверяет, что функция отработала, а не что файла нет
Then('её аудиофайл удалён с диска', async ({ ctx }) => {
  expect(ctx.lastResult.ok).toBe(true);
});

// хорошо: смотрит туда же, куда посмотрел бы человек
Then('её аудиофайл удалён с диска', async ({ ctx }) => {
  await expect(fs.access(ctx.recording.audioPath)).rejects.toThrow();
});
```

Утверждение «нет» (`запись не создаётся`, `я не вижу запись`) проверяет
отсутствие в том месте, где объект появился бы при ошибке, — а не
отсутствие исключения.

## `src/server/` работает в обычном Node

Доменные шаги импортируют сервисы напрямую, в процессе Playwright Test, без
Next.js. Сервис, который тянет рантайм Next.js, в доменном тесте упадёт
при импорте — и сценарий придётся увозить в `@e2e`, в десятки раз
медленнее.

В `src/server/` не использовать `next/headers`, `cookies()`, `headers()`,
`redirect()`, `notFound()` и пакет `server-only`. Всё, что приходит из
запроса, — пользователь, параметры — передаётся в сервис аргументом.
Ошибки сервис бросает как свои доменные ошибки, а в HTTP-ответ или
`notFound()` их переводит обработчик.

```ts
// app/api/recordings/[id]/route.ts — тонкий обработчик
export async function DELETE(
  _req: Request,
  { params }: { params: Promise<{ id: string }> },
) {
  const { id } = await params;
  const user = await requireUser();            // сессия — забота обработчика
  await deleteRecording(user, id);             // логика — в сервисе
  return new Response(null, { status: 204 });
}

// src/server/recordings.ts — обычный TypeScript, без Next.js
export async function deleteRecording(user: User, id: string) { … }
```

## Серверный код

**Владение — в каждом запросе.** Записи и папки личные (BR-22, BR-25).
Фильтр по `ownerId` стоит прямо в `where`, а не «загрузил по id — сравнил
владельца»: второй способ легко забыть в одном месте из двадцати, и это
утечка чужих записей. Чужой объект неотличим от несуществующего: сервис
бросает «не найдено», а не «запрещено», чтобы не подтверждать, что такой
id существует. Сценарии проверяют пару случаев, правило — каждый запрос.

**Доменные ошибки.** Нарушение правила — явная ошибка из `errors.ts`
своей области с понятным текстом. В HTTP-статус её переводит обработчик,
сервис про HTTP не знает.

**Логи доменных событий с id.** Смена статуса записи, сбой провайдера,
неудалённый файл — с id записи. Без этого запись, застрявшую в
`processing`, не расследовать.

**Сначала соседи.** Прежде чем писать новый сервис или шаг, посмотреть,
как устроены соседние в `src/server/` и `steps/`, и повторить их. Новый
слой или новый способ делать то же самое — только по явному решению.

## Пока тестовой обвязки нет

Команды `test:spec` и `test:e2e`, стаб провайдера STT, синхронная обработка
очереди в тестах и отдельная тестовая база появляются в первом вертикальном срезе
(ADR 0003, «Тестовая обвязка»). Если задача пришла раньше, чем они есть, —
сначала тестовая обвязка, потом поведение. Не обходить её «временным» тестом без
Gherkin: временное здесь становится постоянным расхождением.
