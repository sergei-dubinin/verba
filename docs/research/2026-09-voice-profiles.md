# Голосовые профили: узнавание спикеров между записями

- **Дата:** 2026-09-19
- **Статус:** идея на будущее, в MVP не входит. Решение не принято.
- **Вопрос:** можно ли, переименовав спикеров в одной записи («я»,
  «Андрей», «Виктор»), автоматически узнавать этих людей в следующих
  записях. Отправная точка — провайдер AssemblyAI.

## Что есть у AssemblyAI

- **Диаризация** даёт метки `A`, `B`, `C` только в рамках одного файла.
  «Speaker A» в разных записях может быть разными людьми.
- **Speaker Identification** заменяет метки на имена или роли, но по
  содержанию разговора («Андрей, что скажешь?») и списку участников из
  запроса. Голос не сравнивается.
- **Голосовых профилей (enrollment) нет.** В FAQ прямо сказано: узнавание
  человека между файлами пока приходится собирать самостоятельно. Там же
  есть руководство на TitaNet и векторной базе.

Вывод: на AssemblyAI профили делаются своими силами, поверх диаризации.

## Как это устроить

1. **Транскрибация.** Провайдер возвращает реплики с метками спикеров и
   таймкодами (уже есть в MVP).
2. **Эмбеддинги.** По таймкодам вырезаем из исходного аудио куски каждого
   спикера. Берём только чистые реплики от ~1–2 с, без наложения голосов.
   Прогоняем через открытую модель голосовых эмбеддингов: ECAPA-TDNN
   (SpeechBrain), WeSpeaker или TitaNet. На выходе — один эмбеддинг на
   спикера в записи (усреднение по кускам).
3. **Сопоставление.** Сравниваем эмбеддинг с профилями пользователя по
   косинусной близости:
   - выше порога — имя ставится автоматически;
   - серая зона — имя предлагается, пользователь подтверждает;
   - ниже порога — остаётся «Спикер N».
4. **Обучение на правках.** Когда пользователь называет спикера или
   подтверждает предложение, эмбеддинг из этой записи добавляется в
   профиль человека. Храним несколько эмбеддингов на профиль, а не одно
   среднее: так устойчивее к разным микрофонам и помещениям.

Дополнительный сигнал — Speaker Identification провайдера: если имя
прозвучало в разговоре, это подкрепляет совпадение по голосу.

Хранение: эмбеддинг — несколько сотен чисел. Для десятков людей хватает
обычной таблицы в Postgres (или `pgvector`), отдельная векторная база не
нужна.

## Риски и ограничения

- **Порог калибруется на своих данных.** Телефон и ноутбук в переговорке
  заметно сдвигают эмбеддинг.
- **Короткие реплики и наложения** дают плохие эмбеддинги — отбрасывать.
- **Ошибки диаризации.** Если провайдер склеит двух людей в одного спикера,
  эмбеддинг испортит профиль. В профиль добавляем только подтверждённое
  пользователем.
- **Противоречит [ADR 0001](../decisions/0001-external-stt-provider.md)**
  в части «аудио на своём железе не обрабатываем». Модели эмбеддингов лёгкие
  (CPU, секунды на запись), но это отдельный компонент. Нужен новый ADR,
  либо провайдер с профилями в API (см. ниже).
- **Биометрия.** Голосовой профиль — биометрические персональные данные
  (152-ФЗ): для обработки нужно отдельное письменное согласие. Для личного
  использования некритично, для чужих записей — обязательно учесть.
- **Приватность между пользователями.** Профили принадлежат пользователю,
  который их создал, и не видны другим (как записи, BR-22).

## Альтернатива: профили на стороне провайдера

По имеющимся данным (не перепроверено, проверить перед решением):

- **pyannoteAI** — API создаёт voiceprint по образцу и затем
  идентифицирует спикеров по нему.
- **Speechmatics** — возвращает идентификаторы спикеров, которые можно
  передать в следующие запросы для узнавания.

Если профили станут важны, это аргумент при выборе провайдера: сравнивать
не только цену за час, но и объём своего кода на профили.

## Зависимости от MVP

- Нужно переименование спикеров: без него профилю неоткуда взять имя.
  В модели данных задел уже есть (`speaker.name`).
- Исходное аудио хранится (BR-16) — куски для эмбеддингов есть откуда
  вырезать, в том числе для старых записей.
