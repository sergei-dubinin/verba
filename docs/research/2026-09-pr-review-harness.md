# Тестовая обвязка для ревью PR

- **Дата:** 2026-09-24
- **Статус:** предложения, решение не принято. Вернуться после
  вертикального среза 2.

## Проблема

Ревьюер PR получает только диф и текст описания. Всё остальное он
проверяет сам: проходят ли тесты, какие требования закрыты, что
поменялось в сценариях, как выглядят экраны. Тестовая обвязка всё это
знает, но в PR ничего из этого не попадает.

Пример — [PR #2](https://github.com/sergei-dubinin/verba/pull/2)
(вертикальный срез 2): 40 файлов, CI нет, «тесты зелёные» — только
утверждение в описании. Правки сценариев BR-13 и BR-18 — изменения
поведения — теряются среди кода. Сверка экранов с макетами сделана
вручную, и рядом с PR от неё ничего не осталось.

## Предложения

По убыванию пользы.

### 1. CI на каждый PR

GitHub Actions: Postgres как сервис, дальше `pnpm typecheck`, `pnpm lint`,
`pnpm test:spec`, `pnpm test:e2e`, `pnpm build` и проверка, что миграции
совпадают со схемой (`prisma migrate diff --exit-code`). Отчёт Playwright
(`playwright-report/`, трассы) — артефактом запуска, чтобы упавший e2e
можно было разобрать без перезапуска у себя.

Закрывает открытый вопрос «CI» из [architecture.md](../architecture.md).
Там же перечислено, что ещё должно войти в проверку: форматтер и запрет
отключать правило `any` комментарием.

### 2. Статус требований в сводке запуска

Главная идея проекта — статус требования вычисляется прогоном
([ADR 0003](../decisions/0003-executable-scenarios.md)). Но этот статус
нигде не виден. Скрипт читает JSON-отчёт Playwright (reporter `json`) и
выводит в сводку запуска (`$GITHUB_STEP_SUMMARY`) таблицу:

| Требование | Сценариев | Зелёных | Пропущено | Красных |
|---|---|---|---|---|
| BR-13 | 1 | 1 | 0 | 0 |
| BR-14 | 2 | 1 | 1 | 0 |

В идеале — сравнение с `main`: «этот PR закрыл BR-09, BR-10…; ничего не
сломал». Ревьюер за секунды видит, выполняет ли PR обещания плана
вертикального среза.

### 3. Проверка «вертикальный срез готов»

Критерий из каждого плана — «все сценарии с тегами требований среза
выполнены, а не пропущены» — сейчас проверяется глазами. Команда
`pnpm test:slice <N>` берёт требования среза из таблицы в
[docs/plan/README.md](../plan/README.md) и падает, если хоть один
сценарий с этими тегами пропущен или красный. Перенесённые между срезами
сценарии (как `@BR-14 @BR-07`) нужно где-то исключать — например,
списком в той же таблице.

Заодно поправить `pnpm test:missing`: он показывает первые 10 фраз и
пишет «...and 65 more», так что полного списка недостающих шагов не
получить. Нужен полный список, лучше с фильтром по тегам среза.

### 4. Изменённые сценарии — отдельным блоком

Правка `.feature` — изменение поведения и самая важная часть ревью. CI
находит изменённые `.feature` и выносит в сводку сами сценарии: было →
стало. Если в PR меняется `docs/requirements.md`, проверка напоминает:
сценарии с тегом изменённого BR должны быть тронуты или явно оставлены
как есть (правило из [AGENTS.md](../../AGENTS.md), сейчас держится только
на дисциплине).

### 5. Снимки экранов в PR

Автоматизировать сверку с макетами (скилл `verba-ui`, раздел «Сверка с
макетом»): e2e на ключевых состояниях снимает экраны на 390 и 1280 px,
скрипт склеивает их с макетом рядом и кладёт в артефакт запуска.
Ревьюер видит вёрстку, не запуская приложение. Сравнение снимков,
которое роняет сборку при расхождении (visual regression), — позже, когда
экраны устоятся.

### 6. Шаблон PR

`.github/pull_request_template.md`: ссылка на план вертикального среза,
требования, изменённые сценарии с причиной, отступления от макетов,
чекбоксы по документам (`architecture.md`, ADR, `AGENTS.md`, README
сценариев). Отдельная строка для ревьюера: «каждый `Тогда` проверяет
наблюдаемый результат» — это место в цепочке машина не проверит.

## Чего не делать сейчас

- **Мутационное тестирование целиком** (Stryker) — тяжело для проекта
  этого размера. Дешевле выборочная проверка, как в вертикальном
  срезе 2 для BR-22: убрать фильтр по владельцу, убедиться, что сценарии
  покраснели, вернуть. Такие проверки записывать в план среза.
- **Автоматическое ревью кода агентом в CI** — рано. Запускать вручную
  через `/code-review`, когда нужно.

## Предлагаемый порядок

1. Пункты 1–3 одним куском: CI со сводкой требований и командой
   `test:slice`. Сразу виден результат на открытом PR.
2. Пункты 4–6 — следующим шагом.
