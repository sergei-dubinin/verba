# 0002. Стек и хостинг

- **Дата:** 2026-09-20
- **Статус:** принято

## Контекст

Продукт — три экрана ([requirements.md](../requirements.md), NFR-05), одна
фоновая операция (отправка аудио провайдеру и разбор ответа) и десяток
пользователей, заведённых руками. Из ограничений, которые сужают выбор:

- аудио хранится на диске сервера, внешних хранилищ нет (NFR-03) — значит
  нужен постоянный том и отпадает serverless;
- аудио хранится бессрочно (BR-16) — плата за хранение растёт линейно, и
  цена гигабайта становится статьёй расходов;
- ограничений на размер файла нет (BR-21) — загрузка должна стримиться на
  диск, а не собираться в памяти;
- обработка асинхронная, результат приходит вебхуком или опросом
  ([ADR 0001](0001-external-stt-provider.md)) — нужен публичный адрес и
  процесс, переживающий перезапуск;
- Prisma как ORM была выбрана раньше, это фиксирует Node.js и TypeScript.

Форму приложения выбирали между монолитом на Next.js и связкой NestJS API +
Next.js. Второй вариант даёт структуру, навязанную фреймворком, и позволяет
переиспользовать готовый скилл агента под NestJS + Prisma, но платит за это
второй кодовой базой, HTTP-границей с DTO и валидацией, двумя сборками и
двумя деплоями. На трёх экранах эта цена не окупается.

## Решение

- **TypeScript, Node.js LTS.**
- **Next.js (App Router), монолит.** Экраны, серверные обработчики и
  доменный код — одна кодовая база.
- **Правило структуры:** вся логика живёт в `src/server/` (сервисы поверх
  Prisma). Серверные компоненты, route handlers и воркер — тонкие вызовы
  этих сервисов, без бизнес-логики. Фреймворк этого не требует, поэтому
  правило держится ревью и записано в [AGENTS.md](../../AGENTS.md).
- **PostgreSQL + Prisma.** Postgres нужен ради `jsonb` под `provider_raw`
  и каскадов из модели данных.
- **BullMQ + Redis** для фоновой обработки. Воркер — отдельный процесс из
  той же кодовой базы, с теми же сервисами.
- **Хостинг:** один VPS, `docker compose`: `app`, `worker`, `postgres`,
  `redis`, `caddy`. Аудио — на примонтированном томе.
- **Домен:** `memo.dubinin.dev`, TLS автоматически через Caddy.

## Последствия

- Типы между экранами и сервером общие физически: изменение Prisma-модели
  ломает сборку там, где оно ломает поведение. Нет DTO, нет CORS, нет
  версионирования API.
- Если позже понадобится API наружу (MCP-сервер упоминается в
  [архитектуре](../architecture.md) как возможное будущее), он делается
  третьим entrypoint из той же кодовой базы поверх тех же сервисов —
  сетевая граница заранее не нужна.
- Скилл агента под NestJS + Prisma здесь неприменим. Структуру серверного
  кода задаёт правило выше, а не фреймворк; за его соблюдением придётся
  следить.
- Redis нужно запускать с persistence (AOF). Иначе перезапуск сервера
  теряет очередь, и записи навсегда остаются в статусе `processing`.
- Даже с AOF нужен «подметальщик»: периодическая проверка записей, которые
  висят в `processing` дольше разумного, с переводом их в `failed`.
  Пользователь после этого нажмёт повтор (BR-08).
- Загрузку нужно стримить в файл на диске, не буферизуя в память, и снять
  лимит размера тела запроса в Next.js и в Caddy. Многочасовая запись
  иначе положит процесс.
- Вебхук провайдера должен быть доступен снаружи на `memo.dubinin.dev` и
  проверять подпись или секрет в пути: это публичная точка входа.
- Бэкап — это дамп Postgres плюс каталог с аудио. Каталог растёт бессрочно,
  за местом на диске нужно следить; аудио в бэкап целиком, скорее всего,
  не влезет, и это отдельное решение.
- Веб и воркер в одном образе, но разными командами. Масштабирование
  вертикальное: больше CPU и диска на том же VPS.
