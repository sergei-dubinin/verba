# 0004. Сессии входа — строки в базе, в cookie только токен

- **Дата:** 2026-09-23
- **Статус:** принято
- **План:** [вертикальный срез 1](../plan/01-auth.md), решения 1–3

## Контекст

Вход по логину и паролю (BR-23), пользователей заводит администратор
командой (BR-17). Без входа недоступна ни одна страница, кроме страницы
входа (NFR-04). Нужно решить, где живёт сессия и как проверяется вход.

Рассматривали:

- **Подписанная cookie без таблицы** (JWT или зашифрованный payload). Нет
  запроса в базу на каждый запрос, но сессию нельзя отозвать до истечения
  срока. Смена пароля администратором — обычно реакция на утечку, и она
  должна выбивать все сессии.
- **Строка в таблице `session`.** Один индексированный запрос на запрос
  страницы; сессию можно удалить.

## Решение

- **Сессия — строка в `session`**, в httpOnly cookie `verba_session` —
  случайный токен (32 байта). В базе хранится не токен, а его SHA-256:
  утечка базы не даёт готовых сессий.
- **Срок — 30 дней с момента входа**, без продления. Cookie: `httpOnly`,
  `sameSite=lax`, `secure` в production.
- **`user:passwd` удаляет все сессии пользователя.**
- **Пароль — argon2id** (`@node-rs/argon2`, готовые бинарники). Для
  несуществующего логина тоже считается хеш, чтобы по времени ответа
  нельзя было понять, есть ли пользователь. Сообщение об ошибке одно на
  оба случая.
- **Проверка входа — в два слоя**, как советует документация Next.js 16
  (`guides/authentication.md`):
  - `src/proxy.ts` — быстрая проверка без базы: нет cookie → `/login`.
    Не трогает `/login`, `/_next/*`, `/favicon.ico`.
  - `requireUser()` (`src/app/_lib/session.ts`) — настоящая проверка
    сессии через `getSessionUser`; вызывается на каждой защищённой
    странице и в каждом действии.
  - `/login` решает «уже вошёл?» по `getSessionUser`, а не по наличию
    cookie: иначе устаревшая cookie зациклит переадресацию `/` → `/login`
    → `/`.
- **Выхода из системы нет** — его нет ни в требованиях, ни в макетах.

## Последствия

- Запрос в базу на каждую защищённую страницу — один `findUnique` по
  уникальному индексу, для нескольких пользователей несущественно.
- Истёкшие строки `session` не удаляются сами; устаревшая cookie остаётся
  в браузере до следующего входа. Если таблица начнёт расти — чистка по
  `expires_at` в воркере.
- Новая страница без `requireUser()` защищена только proxy (наличие
  cookie). Правило «вызывать `requireUser()` на каждой странице» держится
  ревью.
- Сервисы (`src/server/auth/`) не знают про cookie и Next.js — их
  вызывают доменные шаги в обычном Node.
