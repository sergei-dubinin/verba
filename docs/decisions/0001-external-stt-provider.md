# 0001. Транскрибация и диаризация — через внешний провайдер

- **Дата:** 2026-09-19
- **Статус:** принято
- **Исследование:** [STT + диаризация: провайдеры](../research/2026-09-stt-diarization-providers.md)

## Контекст

Был вариант считать всё локально на Mac (whisperx + pyannote, скрипт
`~/projects/wellness/tools/transcribe.sh`). Он даёт хорошее качество, но
тянет за собой инфраструктуру: ~0.6× от длительности записи на M1 Max,
пик ~15 ГБ памяти, очередь строго по одной задаче, Mac должен быть включён
и доступен с телефона.

## Решение

Аудио на своём железе не обрабатываем. Транскрибацию и диаризацию делает
сторонний сервис. Конкретный провайдер пока не выбран.

При проектировании продукта считаем, что провайдер работает без проблем:
принимает файл, асинхронно возвращает текст со словами, таймингами и
метками спикеров. Особенности конкретного API — лимиты длительности,
форматы, квоты, качество на русском — в обсуждение продукта не тащим и
решаем при выборе провайдера.

## Последствия

- Приложение не привязано к Mac, его можно хостить где угодно.
- Между приложением и провайдером нужен тонкий адаптер, который приводит
  ответ к единому внутреннему формату транскрипта. Сырой ответ провайдера
  храним рядом, чтобы можно было перепарсить.
- Записи уходят третьей стороне, условия обработки данных — один из
  критериев выбора провайдера.
- У каждой записи появляется денежная стоимость (оплата за час аудио).
