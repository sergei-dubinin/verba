# Архитектура verba

- **Обновлено:** 2026-09-24
- **Статус:** черновик. Стек выбран ([ADR 0002](decisions/0002-stack-and-hosting.md)),
  провайдер STT — AssemblyAI, регион EU ([ADR 0005](decisions/0005-assemblyai.md)); в тестах —
  фейк в его формате

## Что делает продукт

Пользователь загружает аудиофайл (в том числе с телефона) и получает
диаризированный транскрипт: текст, разбитый на реплики по спикерам.

Вне рамок MVP:

- нет выбора языка: провайдер определяет язык сам, в режиме с переключением
  языков внутри записи (русская речь с английскими терминами);
- число спикеров не указывается: диаризация определяет его сама;
- нет словаря терминов;
- нет плеера и навигации по аудио;
- нет LLM-обработки текста;
- нет публичных ссылок на транскрипт: всё смотрится в интерфейсе;
- нет MCP-сервера (может появиться позже).

## Интерфейс

Три экрана: вход, список записей, транскрипт записи. Больше ничего.

- **Вход:** логин, пароль, кнопка.
- **Список записей — как Apple Voice Memos.** Строка записи: название, дата,
  длительность, статус, если обработка ещё идёт или упала. Записи
  сгруппированы по датам: «Сегодня», «Вчера», «На этой неделе»
  (календарная неделя с понедельника), дальше по месяцам — «Август 2026»;
  без таблиц и колонок. Одна главная кнопка — «Загрузить».
- **Папки** живут на экране списка, отдельного экрана нет. Сверху
  переключатель: «Все / Без папки / папки пользователя». Переименование и
  удаление папки — из меню в этом переключателе. При загрузке — выпадающий
  список папок с пунктом «+ Новая папка». Перенос записи в другую папку — из
  шапки экрана транскрипта.
- **Транскрипт — как MacWhisper.** Слева узкая колонка: имя спикера (у
  каждого свой цвет) и время начала реплики. Справа текст реплики. Подряд
  идущие реплики одного спикера идут под одним именем, у каждой своё время
  (как несколько сообщений подряд в Telegram, но без пузырей). На телефоне
  колонка превращается в строку над репликой. В шапке — название записи с
  возможностью переименовать и удаление записи.
- **Загрузка** — кнопка «Загрузить» (на телефоне внизу экрана, на
  десктопе в панели), системный выбор файла, шторка (телефон) или диалог
  (десктоп) с именем, размером, длительностью и прогрессом. Параметров
  нет. Не `.m4a` или длиннее 3 часов — сообщение в шторке до отправки.
- **Статус записи** для пользователя — «обрабатывается» (`uploaded` и
  `processing`), «готово», «ошибка» с кнопкой «Повторить» — в строке
  списка и на экране транскрипта. Причина сбоя пользователю не
  показывается. Пока есть запись в обработке, экран перечитывается раз в
  10 с (`router.refresh()`).
- У записи есть автоназвание вида «19 сен, 42 мин, 3 спикера» (дата
  загрузки, длительность, число спикеров, без LLM). Оно не хранится, а
  считается при чтении, если `title` пуст; неизвестные части (спикеры до
  готовности, длительность, если её не удалось прочитать) опускаются. Длительность — до
  минуты, не меньше 1 мин, от часа — «1 ч 04 мин».
- Даты и время показываются в часовом поясе приложения — `Europe/Moscow`
  (`APP_TIME_ZONE` в `src/server/time.ts`), а не сервера и не браузера.
- Сервисы отдают строки, готовые к показу (название, группа, строка
  метаданных, время реплики «00:00:09»), экраны их только раскладывают:
  так всё это проверяется доменными сценариями.
- Чужая, несуществующая запись и id не в формате uuid неотличимы: сервис
  бросает `RecordingNotFoundError`, страница показывает «Запись не
  найдена» со статусом 404.

## Конвейер

```
загрузка аудио → диск сервера → провайдер STT + диаризация
              → адаптер (приводит ответ к нашему формату) → БД → сборка текста
```

1. Пользователь загружает файл: `POST /api/recordings?filename=…`, файл —
   телом запроса, потоком во временный файл на диске
   (`src/server/uploads/upload.ts`). Формат проверяется только по
   расширению `.m4a`, до чтения тела. Когда файл принят целиком, из
   заголовка m4a (бокс `mvhd`, `src/server/audio/m4a.ts`) читается
   длительность: больше 3 часов — отказ (BR-21), не прочиталась —
   запись принимается без длительности. Файл переносится на место,
   создаётся `recording` со статусом `uploaded` и ставится задача в
   очередь. Оборванная загрузка не оставляет ни строки, ни файла.
2. Воркер (`src/worker.ts`) берёт задачу и вызывает `submitRecording`:
   файл уходит провайдеру, `provider_job_id` записывается, статус —
   `processing`. Не удалось отправить за 3 попытки или поставить в
   очередь — `failed`. Если после отправки не удалась запись в базу,
   задача у провайдера осиротеет, а очередь отправит файл ещё раз —
   двойная оплата как цена редкого сбоя. Сироту находят в логе:
   `stt.submitted` без `recording.processing` с тем же `jobId`.
3. Провайдер присылает уведомление на вебхук `POST /api/stt/webhook`
   (`acceptSttNotification`, `src/server/processing/notification.ts`):
   секрет в заголовке `X-Verba-Webhook-Secret` (нет или неверный —
   `401`), в теле — id задачи. Записи с этим id нет — `503`, провайдер
   повторит (уведомление обогнало запись id задачи); иначе ставится
   задача «забрать результат» и ответ `200`. Задача (`fetchSttResult`)
   спрашивает у провайдера состояние и передаёт результат в
   `receiveSttResult`. Без публичного адреса (разработка) уведомлений нет —
   результат забирает проверка незавершённых записей (ниже).
4. `receiveSttResult(jobId, outcome)` (`src/server/recordings/processing.ts`)
   пишет только в запись, которая ждёт (`processing`); иначе — ничего,
   без ошибки: результат принесли и вебхук, и проверка, провайдер
   повторил уведомление или тайм-аут наступил раньше. Статус проверяется
   до разбора. Адаптер разбирает ответ в наш формат (`SttTranscript` в
   `src/server/stt/types.ts`: длительность и реплики с меткой спикера,
   началом, концом, текстом). `completeProcessing` в одной транзакции
   пишет спикеров с `ord` по первому появлению, реплики с `seq` по времени
   начала, сырой ответ в `provider_raw` и ставит статус `done` — условным
   `UPDATE … WHERE status = 'processing'`. Длительность провайдера
   пишется, только если своей, из файла, нет: у AssemblyAI она в целых
   секундах. Сбой провайдера или неразобранный ответ — `failed`, текст
   ошибки и сырой ответ.
5. Как только результат получен или запись упала, данные задачи у
   провайдера удаляются (`forget`): у нас остаются аудио и `provider_raw`.
   Задачу, которая ещё идёт, AssemblyAI не удаляет — её данные удалятся,
   когда придёт поздний результат; не удалилось — `stt.forget_failed` в
   логе с id задачи, удалить руками.
6. Итоговый транскрипт не хранится: он собирается из реплик при запросе.

Разрешённые переходы статуса:

| из | в | когда |
|---|---|---|
| `uploaded` | `processing` | файл отправлен провайдеру |
| `uploaded` | `failed` | очередь недоступна или отправка не удалась за 3 попытки |
| `processing` | `done` | ответ разобран, спикеры и реплики записаны |
| `processing` | `failed` | провайдер вернул ошибку, разбор не удался или запись зависла дольше `STT_TIMEOUT` |
| `failed` | `uploaded` | пользователь запустил обработку повторно (BR-08); дальше тот же путь, что после загрузки |

Любой другой переход — ошибка сервиса, а не молчаливая запись.

Транскрибация — внешний сервис
([ADR 0001](decisions/0001-external-stt-provider.md)), AssemblyAI
([ADR 0005](decisions/0005-assemblyai.md)). Порт —
`src/server/stt/provider.ts`: `submit`, `status`, `forget`,
`parseNotification`, `parse`; выбор реализации — по `STT_PROVIDER`
(`src/server/stt/index.ts`, значения по умолчанию нет): `assemblyai`
(`src/server/stt/assemblyai/client.ts`, свой клиент без SDK, регион EU;
файл уходит потоком через `node:https` — `fetch` Node 22 держит тело в
памяти) или `fake` (`src/server/stt/fake.ts`: всё в памяти, ответ шаг
сценария «кладёт» провайдеру, дальше путь тот же — уведомление или
проверка). Кроме `stt/`, ничто в системе не знает, какой провайдер
используется. Настоящий клиент проверяет `pnpm stt:smoke` — наружу, не в
`pnpm test`.

Очереди — `src/server/processing/queue.ts`, по `VERBA_QUEUE`: `bullmq`
(по умолчанию) или `inline` — сразу, без Redis: тесты и e2e-сервер. По
типам задач, у каждой свой обработчик в воркере:

| очередь | задача | id задачи |
|---|---|---|
| `processing` | отправить запись провайдеру, 3 попытки | id записи |
| `stt-result` | забрать результат по уведомлению, 3 попытки | `result-<jobId>` |
| `sweep` | проверка незавершённых записей, по расписанию, одна за раз | — |

Готовые и упавшие задачи удаляются: иначе повтор (BR-08) или повторное
уведомление BullMQ отбросил бы как дубль.

Проверка незавершённых записей (`sweepProcessing`,
`src/server/processing/sweep.ts`) — раз в `STT_SWEEP_INTERVAL` (5 мин):
- `processing` — сначала спросить провайдера: результат есть — записать
  (потерянное уведомление); ещё идёт дольше `STT_TIMEOUT` (3 ч) с
  последнего перехода — `failed` с `timeout`. Порядок важен: иначе
  тайм-аут провалил бы готовую запись;
- `uploaded` дольше 10 мин — поставить в очередь заново;
- `AUDIO_DIR/tmp/*.part`, не менявшиеся сутки, — удалить.

## Хранение аудио

Аудио лежит на локальном диске сервера (`AUDIO_DIR`) и не удаляется
автоматически: `AUDIO_DIR/{ownerId}/{recordingId}.m4a`, загрузка, которая
ещё идёт, — `AUDIO_DIR/tmp/{uuid}.part`. Раскладку знает только
`src/server/audio/storage.ts`. При
удалении записи пользователем удаляются и файл, и все данные записи
(спикеры, реплики — каскадно). Принимается только формат «Диктофона» на
iPhone: `.m4a` (AAC; при настройке «без потерь» — ALAC), проверяется
только расширение. `moov` у «Диктофона» стоит в конце файла, после
`mdat`, а `mdat` записан с 64-битным размером. Никаких внешних
хранилищ (S3 и т. п.). Провайдеру файл передаётся в теле запроса, публичная
ссылка на файл не нужна.

## Модель данных

### user — пользователь

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| login | text, unique | |
| password_hash | text | хеш пароля argon2id, не сам пароль |
| name | text | |
| created_at | timestamp | |

Регистрации и админки в приложении нет. Пользователя заводит и меняет ему
пароль администратор командами `pnpm user:create <login> [--name "Имя"]` и
`pnpm user:passwd <login>` (`scripts/user.ts`); пароль читается из stdin,
не аргументом. Всё остальное, например переименование или удаление
пользователя, делается в Prisma Studio.

### session — сессия входа

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| user_id | fk → user | `ON DELETE CASCADE` |
| token_hash | text, unique | SHA-256 токена из cookie; сам токен не хранится |
| expires_at | timestamp | 30 дней с момента входа, без продления |
| created_at | timestamp | |

Вход ([ADR 0004](decisions/0004-sessions.md)): в httpOnly cookie
`verba_session` — случайный токен, в базе — его хеш. `user:passwd` удаляет
все сессии пользователя. Проверка — в два слоя: `src/proxy.ts` без базы
отправляет запросы без cookie на `/login`, а `requireUser()`
(`src/app/_lib/session.ts`) проверяет сессию в базе на каждой защищённой
странице и в каждом действии. Выхода из системы нет.

### folder — папка

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| owner_id | fk → user | папки личные |
| name | text | |
| created_at | timestamp | |

Уникальность: `(owner_id, name)`, чтобы у одного пользователя не было двух
папок с одинаковым именем.

### recording — запись

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| owner_id | fk → user | владелец; видит запись только он. Без каскада: пользователя с записями не удалить, иначе на диске останутся файлы без строк |
| folder_id | fk → folder, null | `null` — «Без папки». `ON DELETE CASCADE`: при удалении папки удаляются её записи |
| title | text, null | название от пользователя; если пусто, показывается автоназвание |
| audio_path | text | путь к файлу на диске сервера |
| duration_ms | int, null | длительность из заголовка файла при загрузке; если не прочиталась — от провайдера |
| status | enum | `uploaded` / `processing` / `done` / `failed` |
| error | text, null | причина `failed` |
| provider | text | каким провайдером обработано |
| provider_job_id | text, null, unique | id задачи у провайдера; по нему находят запись вебхук и результат |
| provider_raw | jsonb, null | сырой ответ провайдера, чтобы можно было перепарсить |
| created_at | timestamp | |
| completed_at | timestamp, null | |
| status_changed_at | timestamp | время последнего перехода статуса; от него считают пороги проверки незавершённых записей |

Индекс: `(owner_id, folder_id, created_at)` — для списка записей с фильтром
по папке. Пока папок нет, `folder_id` в таблице нет, а индекс —
`(owner_id, created_at)`; поле и индекс меняются вместе с папками
(вертикальный срез 5).

Каскад в БД удаляет только строки, аудиофайлы на диске он не трогает.
Поэтому удаление папки делается в приложении: собрать `audio_path` всех
записей папки, удалить папку (записи, спикеры и реплики уйдут каскадом),
после коммита удалить файлы. Если файл удалить не удалось, это не ошибка
для пользователя, а мусор на диске: пишем в лог.

Папка записи должна принадлежать владельцу записи. Внешним ключом это не
выразить, поэтому проверяем в приложении при загрузке и переносе записи.

### speaker — спикер в рамках одной записи

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| recording_id | fk → recording | |
| label | text | метка провайдера (`0`, `A`, `spk_1`…) |
| name | text, null | задел на переименование; в MVP всегда пусто |
| ord | int | порядок первого появления: 1, 2, 3… |

Уникальность: `(recording_id, ord)` и `(recording_id, label)`.

Спикер вынесен в отдельную таблицу, а не хранится строкой в реплике: так
переименование спикера, если оно появится, будет одним `UPDATE`, реплики
не трогаются. В MVP спикер всегда показывается как «Спикер {ord}», цвет имени —
`--color-speaker-{(ord − 1) mod 6 + 1}`: палитра на шесть спикеров, дальше
по кругу.

### utterance — реплика

| поле | тип | описание |
|---|---|---|
| id | uuid | |
| recording_id | fk → recording | |
| speaker_id | fk → speaker | кому принадлежит реплика |
| seq | int | порядковый номер в записи |
| start_ms | int | начало от старта записи |
| end_ms | int | конец; длительность = `end_ms - start_ms`, отдельно не хранится |
| text | text | |

Уникальный индекс: `(recording_id, seq)`.

Время хранится целыми миллисекундами, а не float-секундами, чтобы не было
ошибок округления. Конец реплики храним сразу: провайдеры его отдают, а
позже восстановить его неоткуда.

## Сборка транскрипта

```sql
SELECT u.start_ms, u.end_ms, u.text, s.ord, s.name
FROM utterance u JOIN speaker s ON s.id = u.speaker_id
WHERE u.recording_id = $1
ORDER BY u.seq;
```

Подряд идущие реплики одного спикера при выводе группируются под одним
заголовком со спикером, каждая реплика остаётся отдельным абзацем (как
несколько сообщений подряд в Telegram). Провайдеры часто режут речь по
паузам, поэтому такие реплики встречаются часто. В БД они лежат так, как их
отдал провайдер: группировка — задача отображения, а не хранения.

Транскрипт только отображается в интерфейсе, экспорта нет. У каждой
реплики показывается время начала (`start_ms`) от старта записи, всегда
в формате `чч:мм:сс`.

## Стек и развёртывание

Выбор и его обоснование — [ADR 0002](decisions/0002-stack-and-hosting.md).

- **Приложение:** TypeScript, Next.js (App Router), монолит. Вся логика в
  `src/server/`; серверные компоненты, route handlers и воркер — тонкие
  вызовы сервисов.
- **Устройство `src/server/`:** папка на предметную область — `auth/`,
  `recordings/`, `folders/`, `transcript/`, `uploads/`, `stt/`, плюс
  `audio/` (файлы на диске, разбор m4a) и `processing/` (очередь). Внутри —
  сервис, типы и `errors.ts` с доменными ошибками. Провайдера STT знает
  только `stt/`.
- **База:** PostgreSQL через Prisma.
- **Фон:** BullMQ поверх Redis. Воркер — отдельный процесс из той же
  кодовой базы. Redis с включённым AOF, иначе перезапуск теряет очередь.
- **Хостинг:** один VPS, `docker compose`: `app`, `worker`, `postgres`,
  `redis`, `caddy`. Аудио — на примонтированном томе.
- **Домен:** `memo.dubinin.dev`, TLS автоматически через Caddy.

Загрузка стримится на диск, а не буферизуется в памяти: ограничения на
размер файла нет (BR-21). Путь `/api/recordings` исключён из `matcher` у
`proxy`: иначе Next.js держит тело в памяти и молча обрезает его на
10 МБ (проверено: на диск доходит ровно 10 485 760 байт). Вход этот
обработчик проверяет сам и без сессии отвечает `401`. `next start` не
меняет `requestTimeout` Node (300 с): загрузка дольше 5 минут
оборвётся — известное ограничение первой версии (план среза 3,
решение 3). Вебхук провайдера — публичная точка входа на
`memo.dubinin.dev`: путь `/api/stt/webhook` тоже исключён из `proxy`
(у провайдера нет cookie), вход ему заменяет секрет в заголовке.
Заработает с развёртыванием; до тех пор результат забирает проверка.

Записи, застрявшие в `processing` (провайдер не ответил, задача потеряна),
переводит в `failed` проверка незавершённых записей (см. «Конвейер»).
Дальше пользователь запускает обработку повторно (BR-08).

## Открытые вопросы

- CI: где гонять тесты и как выкатывать на VPS. Раннер сценариев выбран в
  [ADR 0003](decisions/0003-executable-scenarios.md). Кроме тестов, в
  проверку должны войти: сборка, линтер (`any` — ошибка, отключать
  правило комментарием нельзя), форматтер, отсутствие расхождения
  миграций со схемой (`prisma migrate diff --exit-code`).
