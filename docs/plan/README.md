# План реализации

- **Обновлено:** 2026-09-24
- **Статус:** вертикальные срезы 1–3 и 3а реализованы (у 3а осталась
  ручная проверка качества на настоящих записях); следующий — 4

Реализация идёт вертикальными срезами (термин — в [AGENTS.md](../../AGENTS.md)).
Вертикальный срез закрыт, когда все сценарии с тегами его требований
зелёные в `test:spec` и `test:e2e`. Статус требования вычисляется
прогоном, а не этим файлом: здесь — порядок и границы вертикальных срезов.

У каждого вертикального среза свой файл с шагами, решениями и критерием
готовности. Файл пишется до кода и правится, если по ходу меняется план.

Порядок: вход первым, потому что шаг «я вошёл как» стоит в предыстории
почти каждого `.feature`, а вертикальный срез маленький — на нём дёшево
обкатать тестовую обвязку. Дальше — главный путь продукта, но с конца:
сначала путь чтения (список и транскрипт), потом загрузка и обработка,
потом управление записями и папки.

Путь чтения идёт раньше загрузки (решение пользователя 2026-09-24): он
проверяется на записях, созданных прямо в базе, без внешней границы —
провайдера STT, очереди, потоковой загрузки. Вертикальный срез загрузки
потом только добавляет вход в уже работающий путь. Результат обработки
записывает сервис из вертикального среза 2, его же вызовет воркер.

Требование может зеленеть частями: BR-02 («Загрузить» с любого экрана
списка) проверяется в том числе на экране папки, поэтому закрывается в
вертикальном срезе 5, хотя кнопка появится в третьем. Такие переносы
отмечаются ниже.

## Перенесено между вертикальными срезами

- **Стаб провайдера STT и синхронная очередь** — по ADR 0003 входят в
  тестовую обвязку первого вертикального среза, перенесены в третий
  (загрузка и обработка): раньше их не на чем проверить. Правка ADR 0003 —
  в вертикальном срезе 2.
- **NFR-04, пример «транскрипт чужой записи»** — в вертикальном срезе 1
  шаг открывает адрес транскрипта со случайным id (модели записи ещё нет).
  Во втором, когда появится модель записи, шаг переделать на настоящую
  запись другого пользователя.
- **BR-22** («пользователь не видит чужую запись», «в списке только свои
  записи») — в `auth.feature`, но нужны записи, список и экран
  транскрипта: вертикальный срез 2.
- **BR-14, «запись видна в списке до конца обработки»** — начинается с
  загрузки файла: вертикальный срез 3. Автоназвание — во втором.
- **Статусы в списке и на экране транскрипта** («обрабатывается»,
  «ошибка», «Повторить») — BR-07, BR-08, вертикальный срез 3. Во втором
  список и транскрипт показывают только готовые записи как следует.
- **BR-02** — кнопка «Загрузить» в третьем вертикальном срезе, сценарий
  целиком — в пятом.
- **Тёмная тема** — не входит в первую версию (решение пользователя
  2026-09-23): макеты `*-dark.html` не верстаются ни в одном вертикальном
  срезе MVP. Отдельная задача после MVP.
- **`upload.feature:21`** — «reco» вместо «verba» в тексте шага: поправить
  в третьем вертикальном срезе.
- **BR-26** (папка при загрузке необязательна) — оба сценария требуют
  папок и фильтра «Без папки»: вертикальный срез 5.
- **Настоящий провайдер STT** — AssemblyAI (решение пользователя
  2026-09-24). В третьем вертикальном срезе — фейк в формате ответа
  AssemblyAI и разбор этого формата; HTTP-клиент, вебхук, «подметальщик»
  зависших записей и ADR 0005 — в вертикальном срезе 3а.
- **Перетаскивание файла на список** (`list-desktop-drag.html`) —
  требованиями не задано, после MVP.
