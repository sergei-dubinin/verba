# Вертикальный срез 2. Список и транскрипт

- **Обновлено:** 2026-09-24
- **Статус:** реализован 2026-09-24: `test:spec` 9/9, `test:e2e` 10/10 зелёные
- **Требования:** BR-09, BR-10, BR-11, BR-12, BR-13, BR-14, BR-18, BR-22
- **Сценарии:** [transcript.feature](../features/transcript.feature)
  целиком; [recordings.feature](../features/recordings.feature) — BR-13 и
  первый сценарий BR-14; [auth.feature](../features/auth.feature) — два
  сценария BR-22 и переделка примера NFR-04 «транскрипт чужой записи»

## Цель

Путь чтения работает от экрана до базы: у пользователя есть готовые
записи — он видит их списком, новые сверху, по группам дат, с
автоназваниями; открывает запись и читает транскрипт по спикерам, со
временем каждой реплики. Чужие записи не видны ни в списке, ни по прямой
ссылке.

Загрузки и обработки в этом вертикальном срезе ещё нет: записи в тестах
создаются прямо в базе, а для ручной проверки — командой с демо-данными
(решение 13). Результат обработки записывает сервис
`completeProcessing` — тот же, который в вертикальном срезе 3 вызовет
воркер (решение 6).

## Решения

Решения 1 и 2 меняют текст сценариев. Пользователь поручил принять их
самому, план со всеми решениями принят пользователем 2026-09-24.

1. **Время реплики — `чч:мм:сс` всегда** («00:00:09»), как в макетах
   `transcript*.html` и в примере из `docs/design-prompt.md`. Сценарий
   BR-18 ждёт «00:09», а `docs/features/README.md` записывает формат
   `мм:сс` и оставляет открытым формат для записей длиннее часа. Один
   формат снимает открытый вопрос, колонка времени одной ширины по всей
   записи (цифры моноширинные), экран совпадает с макетом. Правка:
   `transcript.feature`, BR-18 — «показано время "00:00:09"»; строка в
   «Решениях, принятых в сценариях».
   *Отвергнуто:* `мм:сс`, а после часа `ч:мм:сс` — два формата, колонка
   прыгает по ширине в длинных записях, расходится с макетом.
2. **Группы дат — как в макете и `design-prompt.md`: «Сегодня», «Вчера»,
   «На этой неделе», дальше по месяцам «Август 2026».** Сценарий BR-13 и
   `architecture.md` называют группу «На прошлой неделе», и в сценарии
   она противоречит сама себе: 19 сен 2026 — суббота, 14 сен —
   понедельник той же недели. Правила:
   - «Сегодня», «Вчера» — календарные дни в часовом поясе приложения
     (решение 3);
   - «На этой неделе» — раньше вчерашнего дня, но в текущей календарной
     неделе (с понедельника);
   - остальное — по месяцам: «Сентябрь 2026», месяц в именительном
     падеже, год всегда;
   - порядок групп и записей внутри — по времени загрузки, новые сверху.

   Правка сценария: Ретро (14 сен) — в «На этой неделе»; добавлены две
   записи в «Сегодня» с временем загрузки, чтобы шаг «внутри группы новые
   записи выше старых» было на чём проверить (сейчас в каждой группе по
   одной записи, и шаг проходит на любом порядке); добавлены записи в
   текущий месяц до этой недели и в прошлый месяц. Таблицы шага:

   ```gherkin
   Дано у меня есть записи:
     | название | загружена         |
     | Стендап  | 19 сен 2026 09:48 |
     | Планёрка | 19 сен 2026 14:05 |
     | Иванов   | 18 сен 2026 16:40 |
     | Ретро    | 14 сен 2026 11:00 |
     | Демо     | 10 сен 2026 10:00 |
     | Итоги    | 28 авг 2026 15:30 |
   Когда я открываю список записей
   Тогда записи сгруппированы так:
     | группа         | записи            |
     | Сегодня        | Планёрка, Стендап |
     | Вчера          | Иванов            |
     | На этой неделе | Ретро             |
     | Сентябрь 2026  | Демо              |
     | Август 2026    | Итоги             |
   И внутри группы новые записи выше старых
   ```

   «Стендап» стоит в «Дано» раньше «Планёрки» нарочно: порядок вставки в
   базу не совпадает с ожидаемым порядком на экране.

   **И тег `@e2e` с BR-13 снимается — сценарий доменный.** Группировка
   зависит от «сегодня», а сервер e2e (`next start`) живёт на настоящих
   часах. Сдвигать даты в тестовых данных нельзя: группы по календарным
   неделям и месяцам зависят от дня недели и числа. Доменный сервис
   получает «сейчас» аргументом (решение 4), и сценарий проверяет ровно
   ту логику, которая решает, в какой группе запись. Что список
   показывается на экране, проверяет e2e-шаг «я открываю запись …»:
   он открывает запись кликом из списка (шаг 7).
   *Отвергнуто:* подменять часы сервера cookie, которую приложение читает
   при `VERBA_TEST_CLOCK=1`, — тестовый ход в коде продукта ради одного
   сценария; группировка в браузере под `page.clock` — клиентский
   компонент, расхождение серверного и клиентского рендера около полуночи
   и часовой пояс браузера вместо единого.
3. **Часовой пояс приложения — `Europe/Moscow`, константа
   `APP_TIME_ZONE`** в `src/server/time.ts`. По нему считаются «Сегодня» и
   «Вчера», дата автоназвания, время загрузки в строке списка. Пояс сервера
   (на VPS обычно UTC) не используется. Считается через
   `Intl.DateTimeFormat` с `timeZone`, без библиотек: нужны только
   календарная дата и время в поясе. Названия месяцев — свои массивы:
   `Intl` для `ru` даёт «сент.», а в макетах «сен».
   *Отвергнуто:* пояс браузера — требует клиентского рендера дат и
   синхронизации с сервером; пользователи в одном поясе. Переменная
   окружения — пока не нужна, при необходимости это одна строка.
4. **Сервисы отдают готовые к показу строки, а экраны их только
   раскладывают.** `listRecordings(user, now)` возвращает группы с
   названиями групп, названиями записей и строкой метаданных;
   `getTranscript(user, id)` — название, строку метаданных и группы
   реплик со «Спикер N» и временем «00:00:04». Так BR-13, BR-14, BR-10,
   BR-11 проверяются доменными сценариями за секунды, а в компонентах
   нет логики. «Сейчас» передаётся аргументом: страница вызывает с
   `new Date()`, доменные шаги — с датой из шага «сегодня».
   *Отвергнуто:* сервис отдаёт сырые данные, форматирование в
   компонентах — тогда логика BR-13/14/18 проверялась бы только в e2e.
5. **Модель данных — таблицы `recording`, `speaker`, `utterance` по
   `architecture.md`, кроме `recording.folder_id`** (таблицы `folder`
   ещё нет, поле — в вертикальном срезе 5). Поля загрузки и провайдера
   (`audio_path`, `error`, `provider`, `provider_job_id`,
   `provider_raw`) создаются сейчас, хотя пишутся только в вертикальном
   срезе 3: модель уже спроектирована, одна миграция вместо двух, и
   вертикальный срез 3 не добавляет `NOT NULL`-колонки в таблицу с
   данными. Тестовые данные и демо-данные заполняют `audio_path` и
   `provider` заглушками (`/nonexistent/<id>.m4a`, `"demo"`/`"test"`).
   Уточнения к модели:
   - `status` — enum `recording_status`: `uploaded`, `processing`, `done`,
     `failed`;
   - `recording.owner_id` → `user` без каскада (`RESTRICT`): удалить
     пользователя с записями через Prisma Studio нельзя, пока не удалены
     записи, — иначе на диске останутся файлы без строк;
   - `speaker`, `utterance` → `recording` с `ON DELETE CASCADE` (как в
     `architecture.md`); `utterance.speaker_id` → `speaker` каскадом;
   - уникальность `speaker (recording_id, ord)` и
     `speaker (recording_id, label)`, `utterance (recording_id, seq)` —
     уникальный индекс вместо простого из `architecture.md`;
   - индекс списка — `(owner_id, created_at)`; в вертикальном срезе 5
     станет `(owner_id, folder_id, created_at)`;
   - `speaker.name` — есть, в MVP всегда `null` (задел BR-32).
   *Отвергнуто:* только поля, которые читает этот вертикальный срез, —
   лишняя миграция и `NOT NULL` на заполненной таблице в вертикальном
   срезе 3.
6. **`completeProcessing(recordingId, transcript)` пишется сейчас** —
   для шага «Когда обработка завершилась: длительность 42 минуты,
   спикеров 3» (BR-14). Сервис принимает ответ адаптера в нашем формате
   (`SttTranscript`: длительность и реплики с меткой спикера, началом,
   концом, текстом), в одной транзакции пишет спикеров с `ord` по
   первому появлению, реплики с `seq` по порядку начала, длительность,
   `completed_at` и переводит `processing` → `done`. Другой исходный
   статус — `InvalidStatusTransitionError` (таблица переходов в
   `architecture.md`); переход — условным `UPDATE … WHERE status =
   'processing'`, чтобы две параллельные обработки не записали результат
   дважды. В вертикальном срезе 3 его вызовет воркер, а нумерацию по
   первому появлению проверит сценарий BR-05. Тип `SttTranscript` — в
   `src/server/stt/types.ts`: это контракт адаптера, провайдера он не
   знает.
   *Отвергнуто:* шаг «обработка завершилась» пишет результат прямо в
   базу — «Когда» не вызывал бы продукт, а автоназвание проверялось бы на
   данных, которые продукт никогда так не запишет.
7. **Автоназвание считается при чтении, а не хранится.** `title` в базе —
   только название пользователя; пустое или `null` → автоназвание. Так
   BR-15 («очистка возвращает автоназвание») будет бесплатной. Правила
   (из BR-14 и макетов `list.html`):
   - дата загрузки в поясе приложения: «19 сен», без года;
   - длительность — если известна: минуты округляются до ближайшей, не
     меньше 1: «42 мин»; от часа — «1 ч 04 мин» (минуты двумя цифрами,
     как в макете), ровно час — «2 ч»;
   - спикеры — если запись готова и их больше нуля: «1 спикер»,
     «3 спикера», «5 спикеров», «21 спикер» (обычное правило
     множественного числа);
   - части через запятую: «19 сен, 42 мин, 3 спикера»; без длительности
     и спикеров — просто «19 сен».
   *Отвергнуто:* хранить автоназвание в `title` при завершении
   обработки — пришлось бы отличать его от названия пользователя и
   пересчитывать при очистке (BR-15).
8. **Строка метаданных.** В списке: «14:05 · 42 мин» для «Сегодня» и
   «Вчера», «17 сен, 10:15 · 35 мин» для остальных, «17 сен 2025, 10:15 ·
   35 мин» для прошлых лет (как в `list.html`). В шапке транскрипта:
   «19 сентября, 14:05 · 42 мин · 3 спикера» (месяц полностью, в
   родительном падеже, год — только если не текущий). Часть с папкой из
   макетов («· Альфа — CRM») не показывается до вертикального среза 5.
9. **Чужая и несуществующая запись неотличимы.** `getTranscript` ищет по
   `id` и `owner_id` в одном `where` и бросает `RecordingNotFoundError`
   («Запись не найдена»). Строка, которая не является uuid, — тот же
   `RecordingNotFoundError`, без запроса: Postgres на неё отвечает
   ошибкой типа, и пользователь видел бы 500 вместо 404. Страница
   переводит ошибку в `notFound()`.
10. **Своя страница «не найдено».** Стандартная страница Next 16 следует
    системной теме (`not-found.md` в документации), а тёмной темы в
    первой версии нет. Две страницы по токенам: `src/app/not-found.tsx` —
    «Страница не найдена», `src/app/recordings/[id]/not-found.tsx` —
    «Запись не найдена»; в обеих ссылка «Записи» на `/`. Макета нет —
    отступление: вёрстка как у пустого списка (`list-empty.html`: панель
    с заголовком, строка текста по центру). `loading.tsx` в
    `recordings/[id]/` не делаем: с ним ответ стримится и «не найдено»
    отдаётся со статусом 200.
11. **Экраны — по макетам, с отступлениями** (дополнить при сверке,
    шаг 10):
    - Список на телефоне — `list.html` без чипов папок (вертикальный
      срез 5) и без кнопки «Загрузить» (вертикальный срез 3).
    - Список на десктопе — основная колонка `list-desktop.html` без
      сайдбара, заголовок «Записи», а не «Все записи»: фильтра «Все»
      ещё нет. Колонка по центру, как пустое состояние в вертикальном
      срезе 1.
    - Строки со статусом «обрабатывается» и «ошибка» (текст статуса,
      спиннер, «Повторить») — в вертикальном срезе 3 (BR-07, BR-08).
      Сейчас такие строки показываются без статуса и, как в макете, не
      ссылками. Создать их можно только в базе руками.
    - Шапка транскрипта без кнопки «…» (меню — вертикальные срезы 4 и
      5); ссылка назад — «Записи» и на телефоне, и на десктопе («Все
      записи» появится с папками).
    - Экран транскрипта для записи не в статусе `done` — шапка без тела;
      состояния `transcript-processing.html` и `transcript-error.html` —
      вертикальный срез 3.
    - Цвет спикера — `--color-speaker-{(ord − 1) mod 6 + 1}`: палитра на
      шесть цветов, седьмой спикер получает цвет первого.
    - Размеры, которых нет в токенах (найдено при сверке, шаг 10): колонка
      транскрипта на десктопе 820 px вместо 824
      (`--measure-text − 2 × --space-section`); вертикальный отступ строки
      списка 12 px вместо 11 (телефон) и 13 (десктоп); зазор название →
      метаданные 4 px вместо 3, имя → текст реплики 4 px вместо 6; между
      репликами одного спикера на десктопе 8 px вместо 10; время реплики
      12 px (`.t-fine-print`) вместо 13. На глаз не отличается.
    - Заголовок транскрипта на телефоне — `.t-display-md` с высотой строки
      1.15 из макета; на десктопе — значения `.t-display-lg` числами
      внутри `@media`.
    - Нижний отступ списка на телефоне — `--space-xxl`, а не 120 px из
      макета: там место под кнопку «Загрузить», её ещё нет.
12. **e2e-шаг «я вошёл как …» не заполняет форму, а создаёт сессию
    сервисом и кладёт cookie в браузер.** Вход через форму уже проверяют
    сценарии BR-23; здесь это только подготовка, и она не должна зависеть
    от экрана входа. Пользователь создаётся, если его нет (в
    `transcript.feature` его нет в предыстории).
    *Отвергнуто:* вход через форму в каждом сценарии — медленнее и
    роняет сценарии транскрипта при любой поломке экрана входа.
13. **Демо-данные — команда `pnpm demo:seed <login>`** (`scripts/demo.ts`)
    для сверки с макетами и ручной проверки: записи как в `list.html`
    (разные дни, одна — прошлого месяца) и транскрипт из
    `docs/design-prompt.md`. Записи создаются в статусе `processing` и
    завершаются через `completeProcessing` — тот же путь, что в
    продукте. Команда отказывается работать при
    `NODE_ENV=production`. Это инструмент разработки, а не команда
    администратора; в вертикальном срезе 3 строку записи будет создавать
    сервис загрузки — тогда команда переходит на него.
    *Отвергнуто:* сверять экраны на тестовой базе во время e2e — данных
    одного сценария мало для макета, и их не видно после прогона.
14. **Пагинации нет.** Список отдаёт все записи пользователя: личные
    объёмы — сотни записей, запрос по индексу `(owner_id, created_at)`.
    Вернуться, если список станет медленным.
15. **Порядок вертикальных срезов меняется** (решение пользователя
    2026-09-24): второй — список и транскрипт, третий — загрузка и
    обработка. Путь чтения проверяется на данных из базы без внешней
    границы, и вертикальный срез загрузки потом только добавляет вход в уже
    работающий путь. Правки — в [README](README.md) и ADR 0003 (стаб STT
    и синхронная очередь — в третьем вертикальном срезе).

- **Предыстория `recordings.feature`** — «И сегодня "19 сен 2026"» стоит

  срезу 3 решить: читать длительность из `.m4a` при загрузке или
  отступить от макета. Автоназвание готово к обоим вариантам
  (решение 7).
