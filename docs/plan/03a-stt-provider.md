# Вертикальный срез 3а. Провайдер STT: AssemblyAI

- **Обновлено:** 2026-09-24
- **Статус:** план принят пользователем 2026-09-24 (ревью агентом `Plan`
  пройдено, вопросы закрыты); реализация не начата
- **Требования:** NFR-02 (провайдер — только адаптер); BR-04, BR-08 — на
  настоящем провайдере; BR-08 — зависшие записи
- **Сценарии:** [processing.feature](../features/processing.feature) —
  четыре новых сценария (решение 13); прежние сценарии остаются, их шаги
  переходят на путь через уведомление (решение 12)

## Цель

Записи обрабатывает настоящий AssemblyAI. Файл уходит в AssemblyAI сразу
после загрузки. Когда транскрипт готов, AssemblyAI присылает уведомление
на вебхук, воркер забирает результат, и запись становится «готово».
Если уведомление потерялось, результат забирает периодическая проверка.
Если запись зависла, она переходит в «ошибку», и пользователь нажимает
«Повторить». Данные у AssemblyAI удаляются, как только результат получен.
Кроме `src/server/stt/`, в системе ничего не знает, что провайдер —
AssemblyAI (NFR-02).

Тесты по-прежнему наружу не ходят (ADR 0003): у фейка появляется тот же
путь «уведомление → забрать результат», а настоящий клиент проверяется
командой на живом API (решение 14).

## Сценарии

| Сценарий | Требование | Уровень | Кейсов |
|---|---|---|---|
| настоящий ответ провайдера разбирается без потерь | NFR-02 | spec | 1 |
| результат забирается, даже если уведомление не пришло | BR-04 | spec | 1 |
| зависшая обработка переводится в ошибку | BR-08 | spec | 1 |
| уведомление провайдера без секрета отклоняется | NFR-04 | e2e | 1 |

Текст согласован пользователем 2026-09-24; в `processing.feature` — первым шагом реализации:

```gherkin
  @NFR-02
  Сценарий: настоящий ответ провайдера разбирается без потерь
    Дано я загрузил файл "meeting.m4a"
    Когда провайдер возвращает записанный ответ "assemblyai-demo.json"
    Тогда запись имеет статус "готово"
    И реплика в транскрипте — "Тест, тест, проверка, проверка чай с шарлоткой."

  @BR-04
  Сценарий: результат забирается, даже если уведомление не пришло
    Дано я загрузил файл "meeting.m4a"
    И провайдер закончил обработку, но уведомление не пришло
    Когда проходит проверка незавершённых записей
    Тогда запись имеет статус "готово"

  @BR-08
  Сценарий: зависшая обработка переводится в ошибку
    Дано у меня есть запись, которую провайдер обрабатывает уже 4 часа
    Когда проходит проверка незавершённых записей
    Тогда запись имеет статус "ошибка"
    И мне доступен повторный запуск обработки

  @NFR-04 @e2e
  Сценарий: уведомление провайдера без секрета отклоняется
    Дано у меня есть запись в состоянии "отправлена провайдеру"
    Когда приходит уведомление о готовности этой записи без секрета
    Тогда уведомление отклонено
    И запись по-прежнему обрабатывается
```

- «Записанный ответ» снят AssemblyAI с `demo.m4a`, а это и есть
  `meeting.m4a` — файл переименован в срезе 3. Английских терминов в нём
  нет, поэтому тег `@NFR-02` (адаптер разбирает настоящий формат
  провайдера), а не `@BR-06`.
- `@NFR-04` для вебхука (решение пользователя 2026-09-24): требование
  говорит о страницах без входа, а вебхук — единственная точка входа без
  сессии, и секрет заменяет ему вход. Отдельное требование не заводим.

## Решения

1. **ADR 0005: провайдер — AssemblyAI** (решение пользователя
   2026-09-24). Исследование рекомендовало Deepgram и Speechmatics, выбор
   сделан без сравнительного прогона. ADR записывает выбор и обязательство:
   проверить качество на 2–3 настоящих записях; если качество на русском с
   терминами плохое — вернуться к ADR. Факты из документации AssemblyAI
   (лимиты, вебхуки и их повторы, регион, удаление) со ссылками — в
   `docs/research/2026-09-assemblyai.md`, ссылка в индексе `AGENTS.md`.
2. **Параметры распознавания задаёт адаптер один раз для всех записей**
   (BR-03, BR-05, BR-06): `speaker_labels: true`,
   `language_detection: true`,
   `language_detection_options.code_switching: true`,
   `speech_models: ["universal-3-5-pro", "universal-2"]` (второй —
   запасной для языков вне 18 у 3.5 Pro). Проверено на `demo.m4a`: язык
   `ru`, модель `universal-2`, одна реплика спикера `A`.
   *Проверить:* есть ли русский в Universal-3.5 Pro и что выбирается
   (`speech_model_used`) на русской записи.
3. **Клиент — свой, на `fetch`, без SDK** (`src/server/stt/assemblyai/`):
   - `submit`: `POST /v2/upload` с файлом потоком
     (`fetch(…, { body: stream, duplex: "half" })`) → `upload_url`;
     `POST /v2/transcript` с параметрами решения 2 и вебхуком
     (решение 6) → `id` = `provider_job_id`;
   - `status(jobId)`: `GET /v2/transcript/{id}` → «ещё идёт» /
     `{ ok: true, raw }` / `{ ok: false, reason: error, raw }`; `404` —
     `{ ok: false, reason: "not found" }`;
   - `forget(jobId)`: `DELETE /v2/transcript/{id}` (решение 9);
   - `parseNotification(body) → jobId | null` — тело вебхука
     (`transcript_id`).
   Лимиты AssemblyAI шире наших: `/v2/upload` — до 2,2 ГБ, длительность —
   до 10 ч; у нас 3 ч и около 750 МБ «без потерь».
   *Отвергнуто:* пакет `assemblyai` — зависимость ради четырёх запросов,
   его формат ответа пришлось бы снова приводить к `provider_raw`.
   *Проверить:* `fetch` в Node 22 отправляет поток файла на 750 МБ
   (`duplex: "half"`), не держа его в памяти.
4. **Порт провайдера дополняется** (`src/server/stt/provider.ts`):
   `status(jobId): Promise<{ pending: true } | SttOutcome>`,
   `forget(jobId)`, `parseNotification(body)`; `submit` получает
   `webhookUrl` из настроек. Фейк реализует то же: `status` отдаёт то, что
   шаг сценария «положил» провайдеру (`fakeStt.finish(jobId, raw)`), для
   неизвестного id — «ещё идёт»; `forget` запоминает вызов. Так маршрут
   вебхука и сервисы не знают формата AssemblyAI (NFR-02).
5. **Результат записывается только в запись, которая его ждёт.**
   `receiveSttResult` пишет `provider_raw` и результат одним условным
   `UPDATE … WHERE provider_job_id = … AND status = 'processing'`.
   Запись уже не `processing` (результат забрали вебхук и проверка
   одновременно; AssemblyAI повторил уведомление; тайм-аут наступил
   раньше) — ничего не пишется и не бросается: это отказ от повторной
   обработки, а не ошибка. Сейчас `provider_raw` пишется до перехода
   (`src/server/recordings/processing.ts`) — исправить.
   *Отвергнуто:* поздний результат после тайм-аута превращает `failed` в
   `done` — новый переход в таблице ради редкого случая; пользователь
   нажмёт «Повторить».
6. **Вебхук** — `POST /api/stt/webhook`, логика — в сервисе
   `acceptSttNotification({ secret, body })`, маршрут только передаёт
   заголовок и тело:
   - секрет — заголовок `X-Verba-Webhook-Secret` (при отправке —
     `webhook_auth_header_name/value`), значение — `STT_WEBHOOK_SECRET`,
     сравнение за постоянное время. Секрет не задан в окружении — отказ
     всем. Нет или неверный — `401`, запись не трогается;
   - `parseNotification` → id задачи → поставить задачу «забрать
     результат» и ответить `200`: AssemblyAI ждёт 2xx не дольше 10 с;
   - записи с таким id нет — `503`: 4xx AssemblyAI не повторяет, 5xx —
     до 10 раз раз в 10 с. Так закрывается окно из решения 8 среза 3
     (уведомление пришло раньше, чем записан id задачи). Для старого id
     после повтора (решение 10) это значит 100 с повторов впустую — цена
     приемлемая;
   - запись есть, но не `processing` — `200`, ничего не делаем;
   - очередь недоступна — `503`, AssemblyAI повторит;
   - путь исключается из `matcher` у `proxy`: у AssemblyAI нет cookie, и
     proxy отправил бы его на `/login`.
   `PUBLIC_URL` не задан (разработка на `localhost`) — `webhook_url` не
   передаётся, результат забирает проверка (решение 7).
   *Отвергнуто:* секрет в query-строке — оседает в логах прокси;
   на неизвестный id отвечать `200` и ждать проверки — результат
   задержится до 5 минут без нужды.
7. **Проверка незавершённых записей** — `sweepProcessing(now)` в
   `src/server/processing/`, в воркере — повторяющаяся задача раз в 5 мин
   (`STT_SWEEP_INTERVAL`, в разработке — 30 с). По каждой записи, ошибки
   ловятся по записи, а не на весь проход:
   - `processing` — сначала `status` у провайдера: готово или ошибка →
     `receiveSttResult` (потерянное уведомление). Ещё идёт и с перехода
     прошло больше `STT_TIMEOUT` (по умолчанию 3 ч — решение
     пользователя 2026-09-24) → `failProcessing(
     "timeout")` и `forget`. Порядок важен: иначе тайм-аут провалил бы
     уже готовую запись;
   - `uploaded` дольше 10 мин с перехода — поставить в очередь заново
     (очередь потерялась или воркер лежал); id задачи = id записи;
   - `AUDIO_DIR/tmp/*.part` старше суток — удалить (перенос из решения 4
     среза 3).
   Спрашивать провайдера обо всех записях в `processing` при каждом
   проходе — записей единицы, запрос дешёвый; порога «старше 10 минут»
   нет, иначе потерянное уведомление ждало бы лишние минуты.
   *Отвергнуто:* проверка раз в минуту — лишние запросы; раз в 15 минут —
   долгое ожидание при потерянном уведомлении.
8. **Очереди и задачи — по типам** (сейчас в `src/worker.ts` одна):
   - `processing` — отправка, id задачи = id записи (как в срезе 3);
   - `stt-result` — «забрать результат», id задачи =
     `result-<provider_job_id>`: повторное уведомление не создаст вторую;
     3 попытки, после последней — в лог, дальше подхватит проверка;
   - `sweep` — повторяющаяся проверка, одна задача за раз
     (`upsertJobScheduler`, *проверить* в BullMQ 6).
   У каждой очереди свой обработчик в воркере; `failProcessing` из
   обработчика ошибок — только у `processing`. В режиме `inline` все три
   выполняются сразу.
9. **Данные у AssemblyAI удаляются, как только результат получен или
   запись упала** (решение пользователя 2026-09-24). `forget(jobId)` вызывает сервис — `receiveSttResult` и
   `failProcessing`, — а не воркер, поэтому путь не зависит от того, кто
   принёс результат (вебхук, проверка, `inline`). `DELETE` удаляет
   транскрипт и загруженный файл. У нас остаются аудио и `provider_raw`,
   перепарсить можно без провайдера (ADR 0001). Не удалилось — в лог с
   id задачи: удалить руками; таблицы «что ещё удалить» не заводим.
   *Проверить:* `DELETE` для задачи, которая ещё идёт (тайм-аут), и
   `GET` после `DELETE` — чтобы решение 5 не споткнулось об ответ.
   *Отвергнуто:* хранить у провайдера — записи разговоров у третьей
   стороны без надобности; колонка `provider_forgotten_at` с повтором в
   проверке — сложность ради сбоя `DELETE`, который виден в логе.
10. **Повтор забывает старую задачу.** `retryProcessing` перед сбросом
    `provider_job_id` вызывает `forget` старого id (если он есть). Старое
    уведомление после этого попадёт в «записи с таким id нет» (решение 6).
11. **Модель данных: `recording.status_changed_at`** (timestamp, not null)
    — время последнего перехода статуса. Нужно порогам решения 7 и для
    `uploaded`, и для `processing`: `created_at` не годится после
    повтора. Пишется каждым переходом в `processing.ts`. Миграция
    `recording_status_changed_at` заполняет поле из
    `coalesce(completed_at, created_at)`. Заодно — уникальный индекс на
    `provider_job_id`: по нему ищут вебхук и `receiveSttResult`.
    Шаги подготовки (`steps/support/data.ts`) выставляют поле.
    *Отвергнуто:* `submitted_at` — не покрывает `uploaded`; `updated_at`
    на всю строку — меняется от переименования (срез 4), порог поехал бы.
12. **Шаги «провайдер возвращает …» идут через уведомление.** Шаг кладёт
    ответ фейку (`finish`) и вызывает `acceptSttNotification` с верным
    секретом; синхронная очередь забирает результат. Текст сценариев
    не меняется, путь в тестах совпадает с продуктом, а секрет проверяется
    и в «да»-ветке. `STT_WEBHOOK_SECRET` — в `TEST_ENV`.
    `pnpm stt:deliver` в разработке по-прежнему зовёт `receiveSttResult`
    напрямую: фейк живёт в памяти воркера, а команда — отдельный процесс.
13. **Сценарии** — таблица выше. Новые фразы и что проверяет каждое
    «Тогда» — шаг 6.
14. **Настоящий клиент тестируется командой, а не сценарием:**
    `pnpm stt:smoke` (`scripts/stt.ts smoke`) отправляет `meeting.m4a` в
    AssemblyAI с ключом из `.env`, опрашивает `status` до готовности,
    разбирает ответ, удаляет (`forget`), проверяет, что `GET` после
    удаления не отдаёт текст, и печатает реплики. Платно (секунды аудио),
    наружу — поэтому не в `pnpm test`.
    *Отвергнуто:* сценарий против локального стаба HTTP — проверяет
    стаб, а не AssemblyAI.
15. **Регион — EU** (решение пользователя 2026-09-24):
    `ASSEMBLYAI_BASE_URL`, по умолчанию `https://api.eu.assemblyai.com`.
    Ключ, созданный для США, в EU может не подойти — *проверить* первым
    вызовом `pnpm stt:smoke`; ответ на `demo.m4a` в
    `steps/support/stt/assemblyai-demo.json` снят в США, формат тот же.
    *Отвергнуто:* США (адрес по умолчанию у AssemblyAI) — записи
    разговоров лучше держать в EU.
16. **Развёртывание не входит.** Вебхук заработает, когда появится
    `memo.dubinin.dev` с Caddy (ADR 0002); до тех пор результат забирает
    проверка. Продовый `compose` (`app`, `worker`, `caddy`) и CI —
    отдельный вертикальный срез (открытый вопрос ADR 0002).

## Шаги

### 0. Проверки

- [ ] Universal-3.5 Pro и русский: `speech_model_used` на русской записи;
      `code_switching` для ru/en.
- [ ] `fetch` Node 22 с `duplex: "half"` и `createReadStream`: 750 МБ
      уходят в `/v2/upload` без роста памяти.
- [ ] `DELETE` для незавершённой задачи и `GET` после `DELETE` — что
      отвечает AssemblyAI.
- [ ] Вебхук: заголовок с секретом и тело для `completed` и `error` — на
      живом вызове через туннель или по документации, если туннеля нет.
- [ ] BullMQ 6: `upsertJobScheduler` для повторяющейся задачи; три
      очереди в одном воркере.
- [ ] Ключ из `.env` работает с `api.eu.assemblyai.com` (решение 15).

### 1. Сценарии и документы до кода

- [ ] `processing.feature`: четыре сценария из таблицы.
- [ ] `docs/research/2026-09-assemblyai.md`, ссылка в `AGENTS.md`.
- [ ] ADR 0005.

### 2. Модель данных

- [ ] `recording.status_changed_at` с заполнением, уникальный индекс на
      `provider_job_id`; миграция `recording_status_changed_at`.

### 3. Порт, фейк, сервисы

- [ ] Порт: `status`, `forget`, `parseNotification`, `webhookUrl`; фейк:
      `finish`, `status`, `forget`.
- [ ] `receiveSttResult` — условная запись (решение 5), `forget`;
      `failProcessing` — `forget`; `retryProcessing` — `forget` старого
      id; `status_changed_at` во всех переходах.
- [ ] `acceptSttNotification`, `fetchSttResult(jobId)` (задача
      `stt-result`), `sweepProcessing(now)`.

### 4. Клиент AssemblyAI

- [ ] `src/server/stt/assemblyai/client.ts`; `STT_PROVIDER=assemblyai`;
      `ASSEMBLYAI_API_KEY`, `ASSEMBLYAI_BASE_URL`, `STT_WEBHOOK_SECRET`,
      `PUBLIC_URL`, `STT_TIMEOUT`, `STT_SWEEP_INTERVAL` — в `.env.example`.
- [ ] `pnpm stt:smoke`.

### 5. Точки входа

- [ ] `src/app/api/stt/webhook/route.ts`; `proxy` без этого пути.
- [ ] `src/worker.ts`: три очереди (решение 8).

### 6. Шаги сценариев

- [ ] `провайдер возвращает записанный ответ {string}` — файл из
      `steps/support/stt/` → `finish` → `acceptSttNotification` с секретом.
- [ ] `провайдер закончил обработку, но уведомление не пришло` — только
      `finish`; шаг сам проверяет, что запись ещё `processing`, иначе
      следующий шаг ничего не докажет.
- [ ] `у меня есть запись, которую провайдер обрабатывает уже {int} часа`
      — регуляркой (`час|часа|часов`): `processing` с id задачи,
      `status_changed_at` = сейчас − N ч; у фейка по задаче ничего нет.
- [ ] `проходит проверка незавершённых записей` — `sweepProcessing` с
      «сейчас» из сценария (`ctx.now`) или настоящим временем.
- [ ] «Тогда запись имеет статус …» и «мне доступен повторный запуск» —
      готовые шаги среза 3; для BR-08 дополнительно: у фейка вызван
      `forget` этой задачи.
- [ ] e2e `приходит уведомление о готовности этой записи без секрета` —
      `request.post("/api/stt/webhook", { data: { transcript_id,
      status: "completed" } })` без заголовка; ответ запоминается.
- [ ] e2e `уведомление отклонено` — ответ ровно `401` (не `307` на
      `/login`: так проверяется и исключение из `proxy`).
- [ ] e2e `запись по-прежнему обрабатывается` — в базе `processing`,
      `provider_raw` и `completed_at` пусты.
